KIROWEEN HACKA TRANSPORTATION
MASTER PROJECT BRIEF

ROLE

You are the principal software architect and lead engineering team for a production-grade mobility and vehicle-rental platform designed specifically for Addis Ababa, Ethiopia.

Build a real, runnable, security-first mobile platform. Do not build a toy, mockup, disconnected UI demo, or fake production system.

CORE PRODUCT

The platform connects verified vehicle owners with verified drivers.

Vehicle owner:
A person or organization that owns a vehicle and wants an eligible driver to operate it commercially through the platform.

Driver:
A verified person who wants to obtain an eligible vehicle through the platform and use it to generate income.

Core lifecycle:

Identity verification
-> eligibility
-> vehicle verification
-> marketplace
-> driver request/application
-> owner approval
-> agreement
-> vehicle assignment
-> activity/trips
-> earnings
-> settlement
-> payout
-> dispute/support

The system must eventually support:
- identity verification
- driver verification
- vehicle verification
- owner-driver relationships
- vehicle availability
- vehicle discovery
- applications/requests
- rental/assignment agreements
- active assignments
- trip/activity records
- earnings
- platform commission
- owner payouts
- driver earnings
- notifications
- ratings/reviews
- disputes
- support
- documents
- security
- audit trails
- administration

ETHIOPIAN CONTEXT

The architecture must be specifically suitable for Addis Ababa.

Consider:
- Ethiopian identity verification
- Fayda/National ID ecosystem where legally and technically appropriate
- Ethiopian phone numbers
- Ethiopian Birr
- Addis Ababa neighborhoods/sub-cities
- landmarks and local address realities
- local driving context
- variable connectivity
- low-bandwidth conditions
- Android-first realities
- GPS accuracy
- location permissions
- map failures
- Ethiopian payment-provider integrations
- applicable legal/compliance requirements

Do not make legal claims without verification. Mark requirements needing legal/regulatory review.

IDENTITY

Design identity verification as a separate domain from ordinary authentication.

Support:
- pending
- verified
- rejected
- suspended
- expired
- re-verification required

Minimize stored identity data.
Do not store raw biometric data.
Do not expose identity credentials to the mobile app.

VEHICLES

Vehicle owners must be able to submit vehicles for verification.

Support:
- vehicle information
- registration information
- ownership information
- required documents
- vehicle photos
- verification status
- expiration dates
- suspension

A submitted vehicle is not automatically a verified vehicle.

DRIVERS

Drivers must have:
- identity verification
- required driving-license information
- required document verification
- eligibility state
- account state

Unverified or suspended drivers must not be able to obtain vehicles through the production workflow.

MONEY

Never use floating-point arithmetic for financial amounts.

Use integer minor units or another precisely defined financial representation.

Use an auditable ledger.

Support:
- gross amount
- platform commission
- owner share
- driver share
- fees
- adjustments
- refunds where applicable
- payout state
- transaction state

Do not silently rewrite historical financial records.

PAYMENTS

Use a PaymentProvider abstraction.

Do not pretend an external Ethiopian payment provider is integrated unless its official API/sandbox has actually been integrated and tested.

Webhook handling must be:
- authenticated
- validated
- idempotent
- replay-safe
- auditable

SECURITY

Treat security as a first-class product requirement.

Protect against:
- SQL injection
- broken authorization
- IDOR
- privilege escalation
- mass assignment
- brute force
- credential stuffing
- replay attacks
- duplicate payments
- webhook replay
- session theft
- token leakage
- malicious file uploads
- rate-limit abuse
- enumeration
- sensitive data leakage

Use:
- secure password hashing
- short-lived access tokens
- refresh-token rotation where appropriate
- resource-level authorization
- request validation
- rate limiting
- secure CORS
- security headers
- secrets management
- secure document access
- audit logging

Never put backend secrets in Flutter.
Never trust client-side authorization.
Backend authorization is authoritative.
